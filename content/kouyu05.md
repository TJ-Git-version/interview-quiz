# 05 · 网络与操作系统（口语版）

> 这块中小厂会问、大厂略过，属于「锦上添花」，不用死磕，能说清关键点即可。

---

## 1. TCP 三次握手？为什么不是两次？

**结论**：SYN → SYN+ACK → ACK，确认双方收发都正常。
**展开**：三次握手能**同时确认双方的发送和接收能力**，还能防止「历史连接」把旧 SYN 当成新连接建起来，浪费资源。两次做不到（只能确认一方），所以是三。
**追问备用**：那为什么不是四次？—— 因为三次足以确认双向，第四次是冗余。

---

## 2. TCP 四次挥手？为什么四次？

**结论**：FIN → ACK → FIN → ACK。
**展开**：TCP 是**半关闭**的，一方发 FIN 只表示「我不再发了」，但对方可能还有数据要发，所以要等对方也发 FIN。所以关闭要分两次（双方各一次），一共四次。

---

## 3. HTTP 1.1 / 2 / 3 区别？

**结论**：1.1 有队头阻塞，2 多路复用，3 基于 UDP 的 QUIC 更低延迟。
**展开**：HTTP/1.1 长连接、但同一连接有队头阻塞；HTTP/2 用**二进制分帧 + 多路复用**解决了队头阻塞，还有头部压缩；HTTP/3 基于 QUIC（底层 UDP），连接建立更快、支持连接迁移。**对实时性要求高的场景（比如流式）我会考虑这些。**

---

## 4. TCP 和 UDP 区别？

**结论**：TCP 可靠、面向连接；UDP 快、不可靠。
**展开**：TCP 有可靠传输、有序、流量/拥塞控制，适合文件、网页；UDP 无连接、低延迟、可丢包，适合音视频、实时游戏、DNS。**选型看要不要「可靠」和「低延迟」。**

---

## 5. 进程与线程？epoll？

**结论**：进程是资源单位，线程是调度单位；epoll 事件驱动适合高并发。
**展开**：一个进程多个线程共享地址空间，切换成本比进程低。IO 多路复用里，select/poll 是 O(n) 扫描，epoll 是事件驱动 O(1)，所以 Netty、WebFlux 底层用 epoll，能扛大量连接。**这也解释了为什么响应式能少量线程扛高并发。**

---

## 6. 用户态 / 内核态？

**结论**：CPU 两种运行级别，系统调用要切到内核态。
**展开**：用户态权限低，不能直接访问硬件；要操作文件、网络就得系统调用切到内核态。切换有开销，所以避免频繁系统调用。这也是为什么尽量用内存、批量操作、减少锁。

## 补充 A · 网络高频（面试最常追到，建议优先过）

## 7. TCP 怎么保证可靠传输？【高频追问】

**结论**：靠「确认应答 + 超时重传 + 序号排序去重 + 流量控制 + 拥塞控制」。
**展开**：①发一个包要等 ACK，超时没收到就重传；②每个字节都有序号，接收方能排序、去重，也能知道丢了哪一段；③接收方用窗口大小告诉发送方「我还能收多少」，叫流量控制，防止把接收方打爆；④发送方还要自己探测网络（慢启动、拥塞避免、快重传快恢复），叫拥塞控制，防止把网络打爆。**追问备用**：UDP 需要吗？——不需要，这正是「要可靠选 TCP、要低延迟选 UDP」的底层原因。

---

## 8. 从输入 URL 到页面展示，中间发生了什么？【高频综合题】

**结论**：DNS 解析 → 建立连接（TCP，HTTPS 再加 TLS）→ 发请求 → 服务端处理返回 → 浏览器渲染。
**展开**：①DNS 把域名解析成 IP（浏览器缓存 → hosts → DNS 服务器，逐级递归）；②和服务器 TCP 三次握手，HTTPS 还要多做一次 TLS 握手；③浏览器发 HTTP 请求（方法/header/body）；④服务端处理完返回响应；⑤浏览器解析 HTML、加载 CSS/JS，渲染页面。**结合项目**：我排查「接口慢」就是按这段链路分段看——是 DNS 慢、建连慢、服务端处理慢，还是网关/上游慢；AI 流式接口我还会单独看「首字时间」而不是只看总耗时。

---

## 9. HTTP 和 HTTPS 区别？HTTPS 握手过程？【高频】

**结论**：HTTPS = HTTP + TLS，用「非对称加密换密钥、对称加密传数据」的混合加密。
**展开**：HTTP 明文，能被窃听、篡改；HTTPS 多一层 TLS：①客户端发 ClientHello（支持的加密算法 + 随机数）；②服务端回 ServerHello + 证书（含公钥和 CA 签名）；③客户端验证证书可信后，生成一个随机密钥用服务器公钥加密发过去；④双方用这个密钥做对称加密通信。**为什么混合**：非对称安全但慢，只用来安全地换密钥；正式数据量大，对称加密又快又省。**追问备用**：证书是干嘛的？——防止中间人冒充，CA 签名保证「这个公钥确实是目标服务器的」。**结合项目**：我调通义千问、对外 API 都是 HTTPS，遇到过 SSL 握手超时/证书问题，会先查证书链和代理。

---

## 10. HTTP 状态码 / GET vs POST？【高频速答】

**结论**：2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务端错。
**展开**：常见的有 200 成功；301/302 重定向、304 走缓存；400 参数错、401 未登录、403 无权限、404 不存在、405 方法不支持、429 限流；500 内部错误、502 网关拿不到上游、503 服务不可用、504 网关超时。**结合项目**：我调 AI/外部接口遇到最多的是 502/504——先分清是客户端问题还是网关/上游问题，504 一般去看上游 AI 或数据库是不是太慢。
**GET/POST 速答**：GET 拿数据、参数放 URL、可缓存、幂等；POST 提交/改数据、参数放 body、不缓存。**追问备用**：PUT/DELETE？——语义上 PUT 全量更新、DELETE 删除，都要求幂等。

---

## 11. Cookie / Session / Token（JWT）？分布式会话怎么处理？【高频】

**结论**：Cookie 存客户端，Session 存服务端靠 sessionId 关联，JWT 是「服务端不存」的无状态 token。
**展开**：登录后服务端把登录态放 Session、把 sessionId 写进 Cookie，之后每次请求带上。但 Session 默认在单台内存里，集群部署换个实例就丢了 → 方案二选一：①Session 集中存 Redis（Spring Session），所有实例共享；②改用 JWT，token 里带用户信息 + 签名，服务端验签即可、天然无状态。**结合项目**：我项目里状态共享本来就用 Redis/Redisson，所以走方案①顺手；对外无状态接口走 JWT。**追问备用**：JWT 的坑？——没法主动失效、泄露风险大，所以要短有效期 + refresh token/黑名单；payload 只是 base64 不是加密，别放敏感信息。

## 12. TCP 粘包 / 拆包（半包）？怎么解决？【结合你项目】

**结论**：TCP 是字节流、没有消息边界，会粘包/半包；靠「定长 / 分隔符 / 长度前缀」解决。
**展开**：多个小消息被合在一起发叫粘包，一个大消息分几次到叫半包——TCP 只保证字节顺序，不保证一次收的就是一条完整消息。**结合项目**：我走 TCP/自定义协议（protobuf）时，用「头部 4 字节长度 + 消息体」的帧格式，Netty 里用 LengthFieldBasedFrameDecoder 按长度自动切包；HTTP/WebSocket 这类协议在自己那层已经定义好边界，不用自己处理。**追问备用**：HTTP 为什么没这问题？——HTTP 有 Content-Length/分块传输，WebSocket 有帧头长度，应用层协议自己解决了消息边界。

## 13. WebSocket 原理？长连接为什么要心跳？【结合你实时协作项目】

**结论**：WebSocket 基于 TCP，先 HTTP Upgrade 握手（101），之后双向传帧；长连接要靠心跳保活。
**展开**：客户端先发带 `Upgrade: websocket` 的 HTTP 请求，服务端回 `101 Switching Protocols`，连接升级成 WebSocket 全双工，之后消息按帧走，比 HTTP 轮询省。**为什么心跳**：长连接中间可能被网络设备静默断开（半开连接），服务端一时不知道；所以客户端定时发 ping、服务端回 pong，超时没回就判定断开、清理会话。**结合项目**：我那个组队/即时通信项目就是「按房间维护连接 + 心跳 + 超时清理」，再配合 Redis 存在线状态；这题和 02 里的「SSE vs WebSocket 选型」连起来答。

## 14. 高并发下 TIME_WAIT 过多 / 短连接问题？【结合你压测】

**结论**：主动关闭方会进 TIME_WAIT 等 2MSL；过多本质是「大量短连接 + 主动关闭」，用长连接/连接池解决。
**展开**：TCP 关闭后主动方要停留 2MSL（约 1~2 分钟），保证最后一个 ACK 丢了能重传、旧报文不在新连接里串扰。如果高并发下全是短连接，TIME_WAIT 会占端口和内存，甚至端口不够用。**解决**：①连接池/长连接复用（HTTP keep-alive）；②尽量避免服务端主动 close；③系统参数 tcp_tw_reuse、调小 tcp_fin_timeout 只能谨慎兜底。**结合项目**：我压测 2000 路并发时重点盯连接复用和端口，生产上让连接池复用，而不是每个请求都新建连接。**追问备用**：为什么是 2MSL？——让本端最后一个 ACK 有机会重传 + 让旧连接的报文在网络里过期消失。

## 补充 B · 操作系统（有余力再补，被问概率低于上面）

## 15. 进程间通信 IPC 有哪些？【OS 高频】

**结论**：管道、消息队列、共享内存、信号量、信号、Socket。
**展开**：管道适合有亲缘关系、流式传小数据；消息队列按「条」传递、解耦；共享内存最快但要自己加锁同步（配信号量）；Socket 能跨机器。**结合项目**：Java 跨进程我基本走 Socket/HTTP（RPC、微服务调用本质都是它）；同一个 JVM 内不直接操作这些原语，用线程 + 锁/阻塞队列就够了，和 01 的 JUC 题是一套。

---

## 16. 上下文切换成本高在哪？虚拟线程为什么省？【结合 JDK21 亮点】

**结论**：OS 线程切换要保存/恢复寄存器、缓存失效，还要用户态↔内核态切换，线程多了 CPU 全在切换；虚拟线程把「阻塞等待」变成挂起，成本极低。
**展开**：OS 线程一多，大量 CPU 时间花在切换而不是干活（内核态切换 + 缓存失效）。JDK21 虚拟线程由 JVM 调度，遇到阻塞 IO 就挂起、释放底层平台线程去跑别的，所以几十万路「等 IO」也能扛。**结合项目**：我简历里 JDK21 虚拟线程就是这个价值——SSE、长连接这类大量「等待」的场景，比「一个请求占一个 OS 线程」省得多。**（和 01 的虚拟线程题串着答）**

---

## 17. BIO / NIO / AIO？同步异步 / 阻塞非阻塞？【和 Q5 epoll 连着考】

**结论**：BIO 一连接一线程阻塞等；NIO 用多路复用让一个线程管大量连接；AIO 是异步回调。
**展开**：同步/异步是「结果怎么拿」（自己等 vs 回调通知）；阻塞/非阻塞是「等的时候能不能干别的」。BIO 的 accept/read 都阻塞，连接多了线程爆炸；NIO 靠 select/epoll 事件通知「哪个连接可读了」，一个线程轮询就够——Netty、WebFlux 就是这套，这也把 Q5 的 epoll 补完整了。**追问备用**：Java 的 AIO 为什么用得少？——Linux 下 epoll 已经够高效，AIO 落地和生态一般，实际主流还是 NIO + 多路复用。
