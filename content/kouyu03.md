# 03 · MySQL（口语版）

---

## 1. B+ 树为什么适合索引？

**结论**：多叉、矮胖、叶子有序链表，范围查询快、IO 次数少。
**展开**：普通 B 树非叶子也会存数据，树可能更高；B+ 树把数据全放叶子，非叶子只存索引，所以树更矮、一次 IO 能读更多，而且叶子用链表串起来，范围查询很高效。**这也是 InnoDB 默认用 B+ 树的原因。**

---

## 2. 聚簇索引 vs 二级索引？

**结论**：聚簇索引叶子直接存整行，二级索引存主键值。
**展开**：聚簇索引（一般主键）的叶子节点直接是数据行，一个表只有一个；二级索引叶子存的是主键值，所以查二级索引后要**回表**再取整行（除非是覆盖索引不用回表）。所以我尽量让主键自增，避免页分裂；也尽量用覆盖索引减少回表。

---

## 3. 覆盖索引是什么？

**结论**：要查的列都在索引里，不用回表。
**展开**：通过 explain 看 Extra 是不是 `Using index`，如果是就说明用上了覆盖索引。**优化 SQL 时，我会看能不能把 select 的列都放进索引，规避回表，减少 IO。**

---

## 4. 索引失效场景？【重点】

**结论**：对索引列做函数/运算、隐式转换、前导模糊、没满足最左前缀等。
**展开**：①对索引列用函数或运算（如 `where DATE(col)=...`）；②隐式类型转换（如字符串列用数字比较）；③前导模糊 `%xx`；④联合索引不满足最左前缀；⑤用 `!=`、`not in`；⑥OR 连了非索引列；⑦优化器觉得全表扫更快。
**调优时我会用 explain 看 type 和 Extra，确认是不是真的走了索引。**

---

## 5. explain 怎么看？

**结论**：重点看 type、key、rows、Extra。
**展开**：type 从好到差是 const > eq_ref > ref > range > index > all，越靠右越该优化；key 是实际用的索引；rows 是预估扫描行数；Extra 里 `Using filesort` 或 `Using temporary` 要优化，`Using index` 是覆盖索引。**我定位慢 SQL 就是靠 explain。**

---

## 6. 事务隔离级别？

**结论**：可重复读是 MySQL 默认，靠 MVCC + 间隙锁防幻读。
**展开**：读未提交、读已提交、可重复读、串行化。MySQL 默认可重复读。**快照读（普通 select）用 MVCC 保证可重复读，当前读（for update、update、insert）用间隙锁/临键锁防幻读。** 大多数业务用默认就行。

---

## 7. MVCC 原理？

**结论**：隐藏列 + undo 版本链 + Read View 判断可见性。
**展开**：每一行有隐藏的 trx_id（事务 id）、roll_pointer（回滚指针），指向 undo log 组成的版本链。查询时通过 Read View（活跃事务列表）判断某个版本对当前事务可不可见。**这样读操作不用加锁，性能好。**

---

## 8. 幻读怎么解决？

**结论**：可重复读下，当前读用间隙锁/临键锁锁住范围。
**展开**：快照读靠 MVCC 看快照，不会幻读；但如果是 `select for update`、`update` 这类当前读，就要锁范围。这时候用**间隙锁/临键锁**锁住「一个区间」，防止别的事务在中间插入新行，从而解决幻读。

---

## 9. 锁的类型？

**结论**：表锁 / 行锁（记录、间隙、临键）/ 意向锁；乐观锁 vs 悲观锁。
**展开**：InnoDB 行锁分记录锁（锁一行）、间隙锁（锁区间）、临键锁（记录+区间）。**关键：行锁是基于索引的，如果没走索引，InnoDB 会锁整张表。** 乐观锁用版本号，悲观锁用 `select for update`，看并发冲突大不大来选。

---

## 10. 慢 SQL 怎么优化？【重点，结合你项目】

**结论**：先定位（慢查询日志 + explain），再针对索引和 SQL 改。
**展开**：我会先打开慢查询日志，找到慢语句，然后 explain 看是**缺索引、索引失效、还是深分页 / select \* / 大表全扫**。然后针对改：加/改索引、用覆盖索引、改写 SQL（避免 select *、合理分页、避免大事务）、必要时拆表或做读写分离。**最后再验证执行计划和实际耗时，确保真的快了。**
**【结合项目】**：我做教学素材批量导入、病例查询这些，会特别注意批量插入别一次过大、大表查询别深分页。

---

## 11. 深分页优化？

**结论**：用游标 `where id > ?` 或延迟关联，别让 offset 太大。
**展开**：`limit 100000, 10` 会让 MySQL 扫掉前面 10 万行，浪费。可以改成 `where id > 上一页最大id limit 10`，或用延迟关联先把主键查出来再回表。**这就是分页性能优化最常用的一招。**

---

## 12. 分库分表？

**结论**：数据量大或单表瓶颈时才做，先别轻易拆。
**展开**：有水平（按字段 hash/range 分表）、垂直（按业务拆库）。但会带来**跨库事务、全局 ID（雪花）、分布式查询、路由**等问题。**我的原则是：先优化索引、做读写分离、考虑缓存，实在不够再分库分表。**

---

## 13. 连接池参数怎么调？

**结论**：看并发峰值，避免连接耗尽和超时。
**展开**：核心是 maxActive/maxPoolSize、maxIdle、minIdle、maxWait、连接超时。**我会看服务的峰值和 DB 的连接上限**，别把连接开得比 DB 上限还大，也别太小导致等待。线上要以监控为准调，不能拍脑袋。

---

## 14. 一条 SQL 怎么执行（查询流程）？

**结论**：连接器 → 分析器 → 优化器 → 执行器。
**展开**：先连接器建立连接、做权限校验；分析器做词法/语法分析，生成执行计划树；优化器决定走哪个索引、怎么 join，产出执行计划；执行器再调用存储引擎接口逐行取数据。**所以 explain 看到的执行计划就是优化器选出来的，慢查询往往就卡在「优化器选错索引或全表扫」。** 我调优就是从这条链路定位：到底是哪个环节慢。

---

## 15. update 语句的执行流程 / 为什么 redo 要两阶段提交？【重点】

**结论**：先写 undo log，再改 Buffer Pool 并写 redo log（WAL），最后写 binlog；redo 和 binlog 靠两阶段提交保证一致。
**展开**：update 时，先把旧值写 undo log（供回滚和 MVCC 用），再把新数据改到内存页，接着写 redo log（先写日志再落盘，即 WAL），事务提交后由后台线程把脏页刷盘；binlog 是逻辑日志，记录变更供主从复制。**关键点：redo 和 binlog 不是一份，若只写一份，宕机恢复时会出现「一边有、一边没有」（主从不一致）。所以 MySQL 用两阶段提交：先写 redo log 处于 prepare → 再写 binlog → 最后把 redo 置为 commit。** 这样哪怕是中途宕机，也能根据日志判断该不该提交。

---

## 16. MySQL 日志：redo log / undo log / binlog 区别？【重点】

**结论**：redo 是 InnoDB 物理日志（崩溃恢复），undo 是逻辑日志（回滚/MVCC），binlog 是 Server 层逻辑日志（主从复制/归档）。
**展开**：redo log 记录「页的物理修改」，循环写，配 WAL 保证宕机后已提交数据不丢；undo log 记录「怎么回退」，支持事务回滚和 MVCC 版本链；binlog 记录「逻辑 SQL」，追加写，用于主从复制、数据恢复、Canal 同步。**一句话：binlog 是给别人（从库/同步）看的，redo log 是给自己（恢复）用的，undo log 是给回滚用的。** 被追问「redo 和 binlog 怎么保证一致」，就答两阶段提交。

---

## 17. InnoDB 内存结构：Buffer Pool 是什么？

**结论**：Buffer Pool 是 InnoDB 的内存缓存，读写都先走它，用 LRU 管理，配 change buffer。
**展开**：数据页先读进 Buffer Pool，更新也是先改内存里的页（脏页）再异步刷盘，避免每次直接 IO。Buffer Pool 用 LRU 管理热点页（MySQL 用改进版 LRU，分冷热区，防全表扫把热点页挤掉）；二级索引的写用 change buffer 延迟合并。**调 innodb_buffer_pool_size 是 MySQL 性能调优收益最大的一步，一般给物理内存的 50%~70%。**

---

## 18. 主从复制 / 读写分离 / 主从延迟？

**结论**：主库写 binlog，从库拉 binlog 重放；读写分离把读打到从库；但有主从延迟。
**展开**：主库事务提交时写 binlog，从库的 IO 线程拉 binlog 存到 relay log，SQL 线程再重放。读写分离让主库管写、从库管读，减轻主库压力。**但主从是异步的，从库可能读到旧数据（主从延迟），所以我只在「允许短时不一致」的读场景走从库**（列表、统计），写和强一致读走主库。延迟大可以开并行复制、减少大事务，或核心读仍然走主库。**这对应我项目里读多写少的查询按需做读写分离。**

## 19. 死锁怎么产生、怎么排查、怎么避免？

**结论**：两个事务互相等对方的锁形成环；用死锁日志排查；靠固定加锁顺序、缩小事务来避免。
**展开**：死锁就是「A 等 B 的锁、B 等 A 的锁」。**最常见诱因是加锁顺序不一致**（比如一个先更新 A 再 B，另一个先 B 再 A）。排查看死锁日志里「谁等谁」；InnoDB 会选一个事务回滚（牺牲一个）。避免手法：①统一加锁顺序（按固定字段/主键）；②事务尽量短，别在事务里做慢查询；③用索引让行锁尽量少升级成表锁；④能并行的别串行，降低锁冲突。**我把锁粒度收敛到房间/用户级别，就是在减小死锁面和冲突面。**

---

## 20. char vs varchar、为什么建议自增主键？

**结论**：char 定长、varchar 变长；主键建议自增，避免页分裂。
**展开**：char 定长存储、按固定长度计算和比较，适合长度固定的字段（手机号、状态码）；varchar 按实际内容存并带长度前缀，省空间但多一次长度计算。**主键为什么自增：B+ 树叶子按主键有序，自增主键是追加插入，节点不容易分裂；用 UUID/随机主键会随机插入，频繁页分裂、索引碎片多、IO 大。** 所以能自增就自增，确实需要随机唯一时再权衡（分布式可用雪花 ID）。

---

## 21. count(*) vs count(1) vs count(字段)？

**结论**：count(*) 和 count(1) 差不多（都统计行数）；count(字段) 会跳过 NULL，可能更慢。
**展开**：count(*) 在 InnoDB 里不会真的数所有列，它按「可用的最小索引」统计行数，通常比 count(字段) 快（count(字段) 要判断该字段非 NULL，还会走更宽的索引）；count(1) 等价于 count(*)。**结论：统计行数用 count(*) 就行，count(字段) 是「统计该字段非 NULL 的行数」，语义不同。** 真要快，用缓存或汇总表，别每次 count 大表。

## 22. 为什么用 B+ 树而不是 B 树 / 哈希索引 / 红黑树？（补充第 1 题）

**结论**：B+ 树矮胖 + 叶子链表适合范围查询；哈希只支持等值；红黑树太高、IO 多。
**展开**：①对比 B 树：B+ 非叶子不存数据，一页能装更多索引节点，树更矮，且叶子有序链表做范围查询/排序更方便；②哈希索引等值 O(1) 很快，但没法范围、没法排序，不适合当主索引；③红黑树是二叉，树太高，读一层就是一次 IO，没 B+ 树「多叉矮胖」划算。**所以 InnoDB 默认 B+ 树，同时兼顾等值和范围查询。** 讲这一题时我会先接住第 1 题，把「为什么」补齐。
