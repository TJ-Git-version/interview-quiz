## 一、大模型基础

### 1. 大模型是怎么工作的？

**结论**：预测下一个 token，基于 Transformer 注意力机制。
**展开**：大模型把文本分词成 token，转成向量（embedding），通过**自注意力机制**建模上下文的关联，然后**自回归地预测下一个 token**。它的核心是「给定前面的内容，猜下一个最可能的词」。
**关键概念**：上下文窗口（能接受多少 token）、温度（控制随机性）、思维链 CoT（让模型逐步推理，复杂问题更准）。

---

### 2. 什么是 token？什么是 embedding？

**结论**：token 是模型最小处理单元；embedding 把文本映射成语义向量。
**展开**：token 可能是词或子词，一个中文词可能占 1~2 个 token，所以 token 数不等于字数。embedding 把文本映射成高维向量，**语义相近的向量距离近**。它是 RAG 检索、相似度比较的基础。

---

### 3. 为什么会有幻觉？

**结论**：模型是「预测下一个词」，不是「查数据库」，它可能编造。
**展开**：大模型本质是**生成**，它不知道「事实是什么」，只知道「像什么」，所以在没有可靠信息时可能编造。**解决思路是给它可靠的上下文（RAG），并约束它只能依据检索结果回答。** 这也正是我做 RAG 的原因。

---

## 二、Spring AI

### 4. Spring AI 的 ChatClient / ChatModel / Advisor / ToolCallback？

**结论**：ChatModel 统一底层模型，ChatClient 做流式/易用封装，Advisor 做增强，ToolCallback 接工具。
**展开**：ChatModel 是抽象层，屏蔽不同厂商（通义/OpenAI）差异；ChatClient 是更高层、流式 API，方便拼 prompt、传参；Advisor 能在请求前后做增强（如记忆、RAG、日志、结构化输出）；ToolCallback 把业务函数暴露成模型可调用的工具（Function Calling）。
**【结合项目】**：我项目里用 Spring AI 统一了多模型调用，遇到要换模型或加工具时，业务层不用大改。

---

### 5. 怎么实现流式输出（SSE）？

**结论**：用 ChatModel 的 stream 返回 Flux，Controller 走 text/event-stream。
**展开**：调用 stream 方法得到 Flux（数据流），Spring 把它按 SSE 逐条推给前端，前端用 EventSource 接收，就能**逐 token 渲染**，不用等整段出来。
**【结合项目】**：我临床思维训练里，AI 问诊从「等待式返回」改成流式，首字从 3s 降到 1.2s，体验提升很大。

---

### 6. ChatMemory 对话记忆？

**结论**：存多轮历史，支持持久化，但要控制 token 上限。
**展开**：要让模型记住对话，就得把历史传进去。ChatMemory 负责存和取多轮会话，可持久化到 DB/Redis。**但上下文窗口有限，历史太长我会做压缩/截断/摘要**，避免上下文爆炸、也控制成本。

## 三、RAG（重点，降幻觉必答）

### 7. RAG 完整流程？

**结论**：解析 → 分块 → 向量化 → 检索 → 重排 → 增强生成。
**展开**：文档（PDF/DOCX/TXT）先解析，清洗后**分块**（我用重叠滑窗保证上下文衔接），再用 embedding 向量化存进向量库；用户提问时把问题向量化，检索出最相关的 Top-K，可加 rerank 重排，最后把这些内容拼进 prompt 让模型**基于检索结果生成**，并带引用。
**【结合项目】**：我在 AI 教学智能体里搭的就是这条链路，医学教材/指南/病例导入，支持溯源回答。

---

### 8. 怎么降低幻觉？【重点，必答，结合项目】

**结论**：从「检索质量」和「生成约束」两头抓。
**展开**：
- **检索端**：多路召回（向量 + 关键词 + 查询改写/扩展），尽量多召回相关内容；再 rerank 重排，把最相关的排前面，提高命中。
- **生成端**：提示词**强约束**「只能依据检索结果回答，找不到就拒答」，不编造；回答带**引用来源**（reference），可溯源；检索结果质量差或为空时，**明确拒答**或降级提示。
- **数据端**：知识库质量治理（去重、时效性、覆盖度）。
**一句话**：幻觉没法 100% 消除，我要做的是**让它可控、可溯源、可兜底**。尤其在医学场景，不能瞎给结论。

---

### 9. 分块 chunking 怎么做好？

**结论**：重叠滑窗保证上下文，块大小与检索精度权衡。
**展开**：块太小会丢失上下文，太大又引入噪声、检索不准。我用**带重叠的滑动窗口**，让相邻块共享一点内容，保证语义衔接；同时结合语义/标题切分。**块大小一般要结合检索效果来调，不是固定值。**

---

### 10. 向量库选型？为什么用 pgvector？

**结论**：看数据量、精度、运维成本；我用 pgvector 因为复用 Postgres、简单。
**展开**：pgvector 直接复用 Postgres，免去单独维护一套向量库，还能和业务数据同库、做过滤；Milvus 适合大规模、高性能，但多一个组件；Redis Vector 简单但量小。**我当前教学知识库量级用 pgvector 够用、运维成本低，量大可以平滑迁 Milvus。** 这是基于实际规模做取舍。

---

### 11. 混合检索（向量 + 全文）？

**结论**：向量抓语义，关键词抓精确，两者互补召回更全。
**展开**：向量适合「语义相似」但关键词对不上的；全文检索（或 BM25）适合「明确术语/精确匹配」。我把两者结果**合并去重、rerank**，提高召回率和精度。**教学里专业术语多，混合检索很实用。**

---

### 12. 查询压缩 / 多路查询解决什么？

**结论**：用户问题口语化、模糊、歧义时，改写/扩展能让检索更准。
**展开**：用户问「这个病怎么治」很口语，我把它**改写**成更规范的检索 query，或**扩展**成多个子查询（多路查询），多路去检索再合并，提高命中。**这是 RAG 检索质量的关键优化。**

## 四、Agent / Prompt / MCP

### 13. Agent 是什么？有哪些模式？

**结论**：大模型 + 工具 + 规划 + 记忆 + 循环执行。
**展开**：
- **ReAct**：推理和行动交替，边想边调工具，适合需要探索的任务。
- **Plan-Execute**：先整体规划再逐步执行，适合明确、可拆解的任务。
- **状态机编排**：显式定义状态流转，可控、可中断、可续做。
**【结合项目】**：我做 PPT 生成用**状态机**（意图→结构→大纲→内容→配图→渲染），因为长任务要能断点续做；复杂研究用 **Plan-Execute**。

---

### 14. 多智能体怎么协作？

**结论**：拆成多个专职 Agent，通过编排层 + 统一协议调度。
**展开**：我把它拆成 5 类智能体（临床思维、知识库问答、备课、循证、临床技能），各自专职。通过**统一 SSE 协议**（thinking/text/reference/recommend）和**编排层**调度，可串行可并行，避免上下文爆炸、便于独立迭代。**抽象出 BaseAgent 基类，沉淀记忆、持久化、并发控制，新增 Agent 很快。**

---

### 15. MCP / Function Calling？

**结论**：Function Calling 是模型输出「调工具」请求；MCP 是统一工具接入标准。
**展开**：Function Calling：模型在回答时输出「要调用哪个工具、参数是什么」，应用执行后把结果回填给模型继续推理。MCP（Model Context Protocol）把模型和外部工具/数据源统一成标准协议，工具可复用、可替换。**【结合项目】**：我项目里用 MCP 接 Tavily 做联网搜索，让 Agent 能获取实时信息。

---

### 16. Prompt 工程？

**结论**：角色扮演、Few-shot、结构化输出约束、上下文压缩。
**展开**：我会用**角色扮演**（如让模型扮演患者）、**Few-shot 示例**、**结构化 JSON 输出约束**（保证能解析、能评分）、**上下文压缩**（控制 token）。
**【结合项目】**：我 AI 问诊里配置了可提示词（角色扮演、口语化表达、结构化 JSON），还做提示词优化。**效果评估**用评测集 + 打分（我的结构化评分就是例子），看准确率、幻觉率、首字延迟。

---

### 17. 大模型工程的稳定性问题？

**结论**：幻觉、工具失败、延迟、成本、并发、上下文超限。
**展开**：我主要处理这几点：
- **工具调用失败**：做**有限重试**（不是无限重试，避免卡死）。
- **延迟/首字**：优化前置 stage、复用连接、流式输出。
- **成本**：控制 token、按需选模型（大/小模型）。
- **并发/限流**：多用户同时调用大模型要限流保护（信号量/Sentinel），避免把模型服务打挂。
- **上下文超限**：压缩/分片/摘要。
**【结合项目】**：这些我都在实际 AI 链路里处理过（有限重试、首字优化、并发控制）。

---

### 18. 怎么评价一个大模型应用的好坏？

**结论**：业务指标 + 工程指标 + 可解释性。
**展开**：业务上（准确率、任务完成率、用户满意度）；工程上（首字延迟、总耗时、成本、失败率、幻觉率）；可解释性（引用溯源，回答有出处）。**我会建立评测集来量化，而不是靠人工感觉「好像变好了」。**

## 五、大模型岗高频追问（要能接住）

1. **「你做过的最难的一个大模型问题？」**
  → 我会讲 RAG 降幻觉，或 PPT 长任务断点续做。讲清背景、思路、结果。

2. **「如果检索不到答案怎么办？」**
  → 拒答 + 引导用户 + 记录为知识库缺口，反馈给运营补资料。

3. **「模型回答错了，怎么兜底？」**
  → 提示词约束 + rerank + 引用溯源；高影响场景加人工校验/审核。

4. **「多个用户同时问大模型，怎么保证稳定？」**
  → 限流（信号量/Sentinel）+ 重试 + 降级 + 监控首字延迟/失败率。

5. **「为什么用 RAG 不用微调？」**
  → RAG 快、可溯源、知识更新灵活、成本低；微调适合固定风格/特定能力，但更新知识要重新训练。按需选。

6. **「你的技术选型被质疑了怎么办？」**
  → 先讲清「基于当时规模/约束做取舍」，再承认「若规模更大我会换」，体现判断力。
