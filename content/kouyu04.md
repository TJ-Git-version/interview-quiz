# 04 · Redis 与消息（口语版）

---

## 一、Redis

### 1. Redis 为什么快？

**结论**：内存操作 + 单线程避免锁竞争 + IO 多路复用。
**展开**：数据在内存，读写快；命令单线程执行，避免上下文切换和锁竞争；用 epoll 这种 IO 多路复用处理大量连接。**所以它很适合做缓存、高频状态、计数器这些。**

---

### 2. 常用数据结构及应用？

**结论**：String/Hash/List/Set/Zset，各有对应场景。
**展开**：String 做缓存、计数、分布式锁；Hash 存对象；List 做队列；Set 去重、共同好友；Zset 排行榜、延迟任务。**我的项目里用 Redis 存在线用户、房间成员关系、会话缓存这些高频状态**，就是看图省事、低延迟。

---

### 3. Redis 单线程为什么还这么快？

**结论**：单线程执行命令，但用 IO 多路复用处理连接。
**展开**：它其实是在事件循环里处理命令，连接等 IO 用多路复用，所以不会因为连接多就慢。**但代价是不能有超大 key 和慢命令**，否则会阻塞后面的请求。

---

### 4. 持久化 RDB vs AOF？

**结论**：RDB 快但可能丢数据、AOF 更完整但文件大。
**展开**：RDB 是定时快照，文件小、恢复快，但最后一次可能丢；AOF 是追加写命令，可配 fsync（一般 everysec），数据更完整但文件大。生产常**混合持久化**（RDB 做底 + AOF 增量）。我一般按数据重要性选。

---

### 5. 缓存穿透 / 击穿 / 雪崩？【重点，必答】

**结论**：穿透=查不到的，击穿=热点过期瞬间，雪崩=大批同时失效/宕机。
**展开**：
- **穿透**：查一个**根本不存在**的 key，每次都打到 DB。我加**布隆过滤器**先挡，或者对不存在的 key 缓存空值（短 TTL）。
- **击穿**：**某个热点 key 恰好过期**，一瞬间大量请求打 DB。我用**互斥锁**，只让一个线程重建，其他人等待；或用逻辑过期，key 不主动删，后台异步重建。
- **雪崩**：**一大片 key 同时过期**或 Redis 挂了。我把过期时间**加随机值**打散，再做多级缓存、高可用（哨兵/集群）、限流降级。
**一句话**：穿透解决「查不到」，击穿解决「热点过期瞬间」，雪崩解决「大面积同时失效」。

---

### 6. 缓存一致性？

**结论**：先更新 DB，再删缓存；可接受短暂不一致。
**展开**：常见是旁路缓存：更新数据库后删缓存，下次再读重建。但「更新 DB + 删缓存」不是原子的，可能删了之后又被写回旧值，所以有**延迟双删**（删→等→删）或**订阅 binlog 异步删**。**高并发下能接受短暂不一致**；真要强一致就上锁或版本号，成本高。

---

### 7. 分布式锁实现？【重点】

**结论**：setnx + 唯一标识 + Lua 原子删除；高可靠用 Redisson。
**展开**：用 `setnx` 加锁、设置过期、value 放唯一标识，删除时用 Lua 判断「是这个线程才删」，防止误删别人的锁。**但这套有风险：锁过期但业务没执行完会出问题；主从切换可能丢锁。** 所以我用 **Redisson**，它可重入、有**看门狗自动续期**、支持公平锁。
**【结合项目】**：我组队大厅用「房间粒度」的 Redisson 锁，把并发范围从全局收敛到单房间，冲突少、吞吐高；问诊场景用公平锁，保证学生按顺序，不插队。

---

### 8. Redisson 看门狗是什么？

**结论**：加锁后后台定时续期，业务没跑完锁不被释放。
**展开**：默认锁 30s，Redisson 会起个后台任务在快要到期时自动续期。这样即使业务执行超过初始时间，锁也不会被误释放，避免并发问题。**这是它比手动 setnx 强的地方。**

---

### 9. Redisson vs Redis setnx 锁？

**结论**：Redisson 功能全、更可靠；setnx 简单但功能弱。
**展开**：Redisson 支持可重入、自动续期、公平锁、读写锁，且用 Lua 保证原子；setnx 需要自己处理续期、防误删、公平性。**生产我一般用 Redisson。** 极端高可靠（比如金融）才会考虑 RedLock 或 etcd/ZooKeeper。

---

### 10. big key / 热 key 怎么处理？

**结论**：big key 拆分，热 key 本地缓存 + 限流。
**展开**：大 key 会阻塞 Redis，我会拆分（比如大集合按 hash 分片）、避免存超大对象；热 key 可以用本地缓存分担、多副本、限流。**监控里要盯着这类问题。**

---

## 二、RabbitMQ

### 11. RabbitMQ 工作模型？

**结论**：生产者 → 交换机 → 队列 → 消费者。
**展开**：交换机类型有 direct（精确路由）、topic（通配）、fanout（广播）、headers。我按业务选交换机和 routing key，把消息路由到不同队列。**中间件我还会看消息可靠性和幂等。**

---

### 12. 消息可靠性怎么保证？【重点】

**结论**：生产端 confirm + MQ 持久化 + 消费端手动 ack + 幂等。
**展开**：①生产端开启 confirm，确认消息真的到了 MQ；②交换机、队列、消息都设持久化；③消费端手动 ack，处理成功再确认。**三端配合，保证消息不丢。** 但「不丢」不等于「不重复」，所以还要幂等。

---

### 13. 消息重复消费怎么办（幂等）？

**结论**：消费端用唯一业务 ID 去重。
**展开**：用业务唯一 ID（或消息表）判断「这个业务是否已处理过」，处理过就跳过。可以用 Redis setnx 或 DB 唯一键/状态。**这是保证「同一消息只生效一次」的关键。**

---

### 14. 死信队列 / 延迟队列？

**结论**：消息被拒收、过期、队列满会进死信；延迟队列用 TTL + 死信。
**展开**：死信交换机（DLX）接收这些异常消息，便于排查和补偿。延迟队列可以用「TTL + 死信」实现延迟投递，也可以直接用延迟插件。**我在需要「延迟处理」或「失败补偿」的场景会用。**

---

### 15. 消息堆积怎么处理？

**结论**：加消费者、优化消费逻辑、批量拉取、降级。
**展开**：堆积说明消费速度跟不上生产。我会加消费者/扩容、减少每条消息的处理时间、批量拉取；实在处理不过来就先降级（丢弃或转异步落库）。**线上要监控积压量，提前预警。**


## 三、补充（易漏 / 高频追问）

### 16. Redis 过期删除策略 / 内存淘汰策略？

**结论**：删除是「惰性 + 定期」；内存不够时按淘汰策略删。
**展开**：过期的 key 不会马上删，而是**惰性删除**（被访问到才删）+ **定期删除**（后台抽样删）。但光靠删可能放不下，所以有**内存淘汰**：`noeviction`（默认，写不进就报错）、`allkeys-lru / allkeys-lfu`（对所有 key 挑）、`volatile-lru / volatile-lfu`（只在设置了过期时间的 key 里挑）、`random`。**生产一般 allkeys-lru 或 volatile-lfu**，能保住热点。
**结合项目**：我那些高频状态缓存会配好 `maxmemory` 和淘汰策略，避免 Redis 内存打满后拒绝写入，影响在线状态写入。

---

### 17. Redis 主从复制 / 哨兵 / 集群？

**结论**：主从是副本，哨兵管高可用，集群管分片扩展。
**展开**：**主从复制**让从库备份数据、读写分离、故障时有副本；**哨兵**监控主从，主挂了自动把从提升为主，实现高可用；**集群（Cluster）**把数据分片到多节点，水平扩展、突破单机内存。**取舍**：单机容量够但要高可用用「主从 + 哨兵」；数据量大、要横向扩展才上集群。**代价**：主从切换可能丢锁、有短暂不一致，所以分布式锁不能只靠单点。
**结合项目**：我先在单机保证数据可靠（RDB/AOF + 后台备份），量级上来再引入哨兵/集群，而不是一开始就上复杂架构。

---

### 18. Redis Pub/Sub 和 MQ 的区别？（跨节点事件分发）

**结论**：Pub/Sub 是即时广播、不持久化；MQ 能持久化、可重试、可回溯。
**展开**：Redis Pub/Sub 做**发布/订阅广播**，消息发出去没人订阅就丢了，**不落盘、不重试、不做消费确认**。RabbitMQ 这类 MQ 支持**持久化、手动 ack、重试、死信、堆积**，适合要求「不丢、可补偿」的可靠消息。所以**能接受丢、要低延迟广播**用 Pub/Sub；**要可靠、要兜底补偿**用 MQ。
**【结合项目】**：我协作平台的多节点 WebSocket，需要把某房间的加入/退出/消息**跨节点广播**，就用 **Redis Pub/Sub**（按房间做 channel）做事件分发，简单够用；如果要做离线消息、持久化补发，才会落到 **MQ**。

---

### 19. RabbitMQ vs Kafka？怎么选？

**结论**：看吞吐、路由、是否要可回溯重放。
**展开**：**RabbitMQ** 路由灵活（direct/topic/fanout）、延迟低，适合**业务解耦、任务分发、需要精细路由**的场景；**Kafka** 吞吐极高、支持**分区顺序、消息可回溯/重放**，适合**日志、埋点、流处理**这类大数据场景。我要「路由精确到 routing key、任务及时处理」选 RabbitMQ；要「海量数据、可重放做分析」才上 Kafka。
**取舍**：我的业务是教学协作、短消息、更看重及时性和路由，所以 RabbitMQ 合适；如果做埋点/日志采集这种量大、要重放的，我才用 Kafka。

---

### 20. 消息顺序怎么保证？

**结论**：MQ 只能保证「单队列/单分区」内有序，不同队列/分区之间不保证。
**展开**：RabbitMQ 用**单队列 + 单消费者**，或把同一业务键路由到同一队列；Kafka 用**同一 key 进同一分区**，保证该 key 有序。**代价**：有序和并发/吞吐是矛盾的，强有序就要牺牲并发，所以尽量**按业务拆细粒度**，让有序范围收敛到一条链路上。
**【结合项目】**：我协作平台同一个房间的消息不能前后串，我就**按房间做路由/分区**，让同一房间的消息落在同一条消费链路，既保证顺序，又没必要全局串行。

## 四、补充 2（本次遗漏的高频追问 / 追问层，追加在最后）

### 21. Redis 的单线程到底指什么？6.0 为什么又引入多线程？（补充第 3 题）【高频追问】

**结论**：单线程指「命令执行」这条主链路；6.0 的多线程只做网络 IO，命令执行仍是单线程。

**展开**：真正单线程的是**命令执行 + 数据结构操作**，靠事件循环串行处理，所以没有锁竞争、没有上下文切换；但「网络读写、协议解析」这层在大连接数下会成瓶颈，**Redis 6.0 引入多线程 IO（io-threads 可配），只负责收发包/解析，命令还是单线程执行**。一句话：多线程解的是「网络 IO」的吞吐，不是「命令执行」的并发，所以第 3 题「单线程也快」的结论依然成立。

---

### 22. 数据结构底层是什么？Zset 为什么用跳表？【重点】

**结论**：String 底层是 SDS；Hash/List/Zset/Set 小数据用紧凑编码省内存，大了转哈希表/跳表等常规结构；Zset 是「跳表 + 哈希表」组合。

**展开**：SDS 比 C 字符串多存了长度，O(1) 取长度、二进制安全；小数据用 listpack/quicklist/intset 这类**紧凑编码**，达到阈值再转哈希表、跳表，兼顾省内存和性能。**Zset 用跳表按 score 维护有序 + 哈希表存 member→score，做排名/范围是 O(logN)**。为什么不用红黑树/B+ 树：红黑树实现复杂、范围遍历要中序走；B+ 树是为磁盘 IO 设计的「矮胖多叉」，Redis 在内存里用跳表**实现简单、好调层数、天然支持范围遍历**，更划算。

---

### 23. 缓存更新有哪几种模式？（补充第 6 题）

**结论**：最常用 Cache Aside（旁路缓存）；还有 Read Through / Write Through / Write Behind，各有取舍。

**展开**：Cache Aside 是应用自己管缓存——读 miss 回源 DB 再写缓存，写先更 DB 再删缓存（就是第 6 题那套）；**Read Through** 是缓存组件自己负责回源，应用只读写缓存；**Write Through** 写 DB 时同步写缓存，一致性最好但写路径变慢；**Write Behind** 先写缓存、异步批量落 DB，性能最高但宕机会丢。取舍：**我线上用 Cache Aside**，简单可控、能接受短暂不一致；要极致读性能/抗热点才上「本地缓存 + 异步写」。

---

### 24. Redis 事务 / pipeline / Lua 的区别？

**结论**：事务保证多条命令原子执行但不回滚；pipeline 只是批量发命令省 RTT；Lua 把逻辑塞进服务端原子执行，最灵活。

**展开**：`MULTI/EXEC` 把命令打包按序执行、中间不插别的命令，但**运行出错不回滚、也不能做条件判断**；pipeline 只是客户端一次把多条命令发出去，省网络往返，**不保证原子**；Lua 脚本在服务端整段执行**天然原子**，还能写 if/while 做判断。**取舍：带判断的原子操作（如分布式锁释放「判断再删」）用 Lua；只是批量读写省 RTT 用 pipeline；事务我基本不用。** 一句话：pipeline 省时间，Lua 保原子。

---

### 25. 主从复制怎么同步？哨兵怎么选主？脑裂会丢什么？（补充第 17 题）【重点】

**结论**：同步分「全量 + 增量」两段；哨兵靠投票把从库提升为主；主从切换存在脑裂丢数据风险。

**展开**：从库第一次连主库走**全量同步**（主库 bgsave 出 RDB 给从库，期间的增量用 backlog 补）；之后是**增量同步**——主库把写命令放进 repl backlog 缓冲区，从库断线重连后从断点续拉，追不上才重新全量。哨兵先**主观下线**（单个哨兵觉得主挂了），多数哨兵确认后变**客观下线**，再选出一个哨兵当 leader，按「从库优先级 → 复制偏移量 → runid」挑新主。**风险：旧主假死被切后可能又恢复，两边同时写造成脑裂，切换后没同步过去的数据会丢**，所以分布式锁这类强一致数据不能只信 Redis 主从（呼应第 7 题）。

---

### 26. Cluster 的哈希槽是什么？扩容/迁移时 MOVED 和 ASK？（补充第 17 题）

**结论**：Cluster 把 16384 个槽分到各节点，key 用 CRC16 取模落到槽；迁移时用 MOVED/ASK 做重定向。

**展开**：`CRC16(key) % 16384` 算出槽，槽归哪个节点就直连哪个节点，所以加节点就是把一部分槽和槽上的数据迁过去，实现水平扩展。迁移过程中会碰到两种返回：**槽已完全归新节点管 → 返回 MOVED**（客户端要更新本地路由缓存，以后都找新节点）；**槽正在迁移、key 刚好已在新节点 → 返回 ASK**（只本次去新节点找）。一句话：**MOVED 是「以后都去那」，ASK 是「就这一次去那」。**

---

### 27. 用 Redis 自己实现延迟队列？（呼应第 14 题）

**结论**：用 Zset 可以做：score 存到期时间戳，轮询取到期的任务；但不如 MQ 可靠。

**展开**：Zset 的 member 存任务内容、score 存「到期时间」，后台定时 `zrangebyscore` 取 score ≤ 当前时间的任务出来处理。**简单够用，但没有 ack/重试/死信，进程一挂任务可能丢**，只适合能接受丢失的轻量场景。取舍：**轻量、可接受丢 → Zset 临时顶；要可靠投递、失败补偿 → RabbitMQ（TTL + 死信或延迟插件，第 14 题）**。

---

### 28. 为什么要用 MQ？会带来什么问题？【必答，常被当开场第一问】

**结论**：解耦、异步、削峰；代价是引入「不丢、不重、有序、最终一致」一堆新问题。

**展开**：①**解耦**——生产者发消息，消费者各自订阅，互不感知、可随时增减；②**异步**——发通知/写日志这类非核心链路不阻塞主流程；③**削峰**——瞬时高并发先堆进队列，消费端按自己的处理能力慢慢消费。**代价：多一个组件就多一个挂点（要高可用）；消息可能重复（要幂等）；可能乱序（要单队列/分区）；生产者成功 ≠ 消费者成功（要最终一致）。** 一句话：MQ 把「同步强耦合调用」换成「异步的最终一致」。

---

### 29. 消费失败怎么处理？ack / nack / requeue / 重试？（追问第 12 题）【重点】

**结论**：手动 ack，成功才确认；失败按策略重试，超阈值进死信；再用 prefetch 做消费端限流。

**展开**：手动 ack 下：**处理成功 → ack**；业务失败能重试 → **nack/reject**，但**不要无脑 requeue**（会原地死循环），我一般是**记录重试次数，超过 N 次不 requeue、进死信队列**，由补偿任务处理（呼应第 14 题）。**prefetch（QoS）**限制每个消费者未确认消息数，防止消息一次性全推给慢消费者把进程拖垮。一句话：**ack 管不丢，重试 + 死信管失败兜底，prefetch 管别撑死消费者。**

---

### 30. 消息最终一致怎么做？（本地消息表 / 事务消息 / 对账）【重点】

**结论**：核心是「生产者侧保证消息一定能发出去 + 消费端幂等」，常用本地消息表 + 定时重发，或 MQ 事务消息。

**展开**：①**本地消息表**——业务表和消息表放同一个本地事务一起提交，后台定时扫未发送的消息补发到 MQ，消费端做幂等（第 13 题）；②**事务消息**——RocketMQ 支持：先发半消息，本地事务成功再 commit、失败 rollback，MQ 还会回查；RabbitMQ 没有原生半消息，用事务/confirm 近似；③**定时对账兜底**——定期把「消息」和「业务处理结果」对一遍，发现漏的补偿。一句话：**本地消息表最通用、事务消息最顺滑、对账是最后保险。**

### 31. RabbitMQ 高可用怎么做？

**结论**：节点组集群 + 队列开镜像/仲裁多副本，单节点挂了不丢消息、自动选主。

**展开**：RabbitMQ 集群节点间共享交换机/元数据，但**普通集群队列只在一个节点上**（其他节点只是转发），那节点挂了队列就不可用；所以要给重要队列做**镜像队列**（主从复制）或官方更推荐的**仲裁队列 Quorum Queue**（Raft 多副本、强一致），节点挂了自动选主。取舍：镜像队列实现简单但同步可能不一致、新版本已不建议；**仲裁队列基于 Raft、一致性好，是当前推荐**。我生产会「集群 + 仲裁队列」，再配合 confirm/ack（第 12 题）做到端到端不丢。

### 32. 既然对比了 Kafka：Kafka 为什么快？（补充第 19 题）

**结论**：顺序写盘 + Page Cache + 零拷贝 + 批量/分区并行，是叠出来的快。

**展开**：①Kafka 只**追加写日志**，顺序 IO 比随机 IO 快一个量级；②读写走操作系统 **Page Cache**，不每笔都刷盘；③消费时用 **sendfile 零拷贝**，数据从磁盘到网卡不经过用户态拷贝；④生产端**批量发送 + 压缩**，消费端多分区并行。**定位差异：Kafka 更像「可重放的日志」，靠 offset 标记消费位置、能回溯；RabbitMQ 是「投递即删的任务队列」。** 所以日志/埋点/流处理用 Kafka，业务任务分发用 RabbitMQ。

### 33. Kafka 消费组 / offset 怎么保证不丢不重？

**结论**：同一消费组里一个分区同一时刻只给一个消费者；offset 提交时机决定「不丢」还是「不重」，最终还得消费端幂等兜底。

**展开**：消费组内**分区被组内消费者分摊**，加消费者能并行，但**消费者数超过分区数就白加**；offset 记的是「消费到哪了」——**先处理再提交 offset：宕机重来会重复消费；先提交再处理：宕机会丢**，跟 RabbitMQ 一样靠**消费端幂等**（第 13 题）解决重复。一句话：**Kafka 只保证分区内有序，「不丢不重」最终还得靠幂等。**
