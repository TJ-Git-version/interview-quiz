# 项目 STAR 深挖

> 用法：每个项目准备「一句话（30s）/ 2 分钟版 / 5 分钟深挖版」三个粒度，且每个项目至少背熟 10 条追问答案。
> 面试时：先用一句话抓住对方兴趣 → 对方追问再进 2 分钟 / 5 分钟版。
> 所有指标（院校数/学员数/训练次数/首字延迟/吞吐）请按你简历真实数据，做到**随口能报、来源可信**。

---

## 项目总览（面试开场前，3 句话把三个项目串起来）

> 「我在妙创两年，围绕医疗 AI 教学做了三个相互递进的项目：最开始是**单点能力**（AI 临床思维训练：病例库→AI 问诊→智能评价→报告闭环），然后做了**多人在线协作**（传染病协同：房间 + 实时通信），最后把经验沉淀成**平台**（AI 医学教学智能体：5 类智能体 + RAG + PPT 状态机）。这个递进过程，也正好对应我从『做功能』到『做平台』的能力升级。」

# 项目一 · AI 医学教学智能体平台（主推）

## 一句话版（30s）
> 「面向医学院校的一体化 AI 教学平台，我把医学教学需求抽象成 5 类智能体（临床思维、知识库问答、智能备课、循证研究、临床技能），用多智能体 + 统一 SSE 协议 + RAG + PPT 状态机，从 0 到 1 搭了个可扩展的底座。我是技术负责人，主导调研、架构到落地。」

## 2 分钟版（STAR）
- **S 背景**：医学教学需要 24h AI 助教 + 教员智能备课，但传统系统零散、无法覆盖五大场景、难以复用。
- **T 目标**：做一个「通用底座 + 医学场景」的一体化平台，让新场景能快速加，且问答要可溯源、少幻觉。
- **A 行动（4 点）**：
  1. 主导场景调研，抽象出 5 类智能体能力，设计**分层多智能体架构**与**统一 SSE 协议**（thinking / text / reference / recommend 四类消息）。
  2. 抽象 **BaseAgent 基类**，沉淀对话记忆、会话持久化、并发控制等公共能力，新 Agent 可快速扩展。
  3. 搭建 **RAG 全链路**：PDF/DOCX/TXT 解析 → 重叠分块 → Qwen embedding 向量化 → pgvector 检索 → 增强生成，集成查询压缩与多路召回。
  4. 实现 **PPT 生成状态机**（意图识别/结构/大纲/内容/配图/渲染），支持 CREATE / MODIFY / RESUME 断点续做与双渲染引擎；并实现 Plan-Execute 深度研究与可扩展技能库。
- **R 结果**：xx 篇医学知识库、xx+ 教学课件、首字响应 <1.6s、长任务断点续做、试点覆盖 xx 师生、xx 万次会话；教员备课从 4 小时降到 30 分钟。
- **T（学到/沉淀）**：从「做功能」升级到「做平台」，学会了抽象公共能力、统一协议、把可控性与可扩展性考虑进架构。

## 5 分钟深挖版（再加：难点、取舍、排查、扩展）
- **难点 1：多智能体怎么不失控？** → 用「统一 SSE 协议 + BaseAgent 基类」收口，所有 Agent 走同一套消息和生命周期，避免各自为政。
- **难点 2：RAG 降幻觉。** → 多路召回 + 引用溯源（reference）+ 无结果拒答 + 提示词强约束。
- **难点 3：长任务（PPT）中断续做。** → 状态机 + 任务去重 + 断点持久化。
- **取舍**：用 pgvector 而非 Milvus（复用 Postgres、运维成本低，针对当前量级「够用」；量大再迁）。
- **扩展**：新增一个教学场景 = 新增一个 Agent（继承 BaseAgent + 配置 prompt + 注册），不动公共层。

## 高频追问 + 答案（10+）
1. **为什么用多智能体，不直接一个大 prompt？**
  → 拆分职责可独立迭代、能并行、prompt 更短更可控、便于定位问题；单个大 prompt 一旦长就难维护、易串场景。
2. **BaseAgent 抽象了哪些公共能力？**
  → 对话记忆（ChatMemory）、会话持久化、并发控制（幂等/去重）、统一 SSE 消息输出；子类只需实现业务动作。
3. **统一 SSE 协议为什么分 thinking/text/reference/recommend？**
  → thinking 给「思考过程」、text 给「正文」、reference 给「溯源引用」、recommend 给「推荐」，前端能分别渲染，用户体验和可控性都更好。
4. **RAG 怎么降幻觉？具体哪几步？**
  → ①多路召回（向量+关键词+查询扩展）提高命中 ②rerank 排优 ③提示词强约束「必须引用检索结果」 ④reference 溯源可查 ⑤无结果时拒答（I don't know） ⑥检索失败降级提示。
5. **PPT 生成为什么用状态机？**
  → 长任务可中断、可断点续做、可回滚；每个状态明确可重试，进度可上报；避免「一条长 prompt 到底」难控难查。
6. **断点续做怎么实现？**
  → 把每个状态（结构/大纲/内容/配图/渲染）的结果持久化，任务中断后从上次成功状态继续；用任务 ID 去重，避免重复生成。
7. **为什么选 pgvector，不选 Milvus/Redis Vector？**
  → 复用了 Postgres 生态、免额外运维向量库、与业务数据同库便于事务；当前知识库量级够用，量大可平滑迁 Milvus。
8. **查询压缩/多路召回解决什么问题？**
  → 用户口语化、长问题、歧义问题检索不准；改写+扩展+多路召回提高召回率，再重排提精度。
9. **并发控制怎么做？会话级任务去重？**
  → Redis/Redisson 做会话级互斥与幂等，防止同一会话重复触发长任务；配合优雅中断释放资源。
10. **全链路日志/首字延迟/工具调用统计怎么做？**
  → 关键节点埋点，记录 LLM 首字时间、总耗时、工具调用次数，便于监控与优化（也用于向业务证明效果）。
11. **多智能体之间怎么通信/协作？**
  → 通过统一消息协议与编排层调度；子任务可按需串行/并行，结果回填上下文，避免造成上下文爆炸。
12. **如果现在让你重做，会改什么？**
  → 会更早引入「评测集」来量化 RAG/Agent 效果，而不是靠人工感知；并用更完善的监控（成本、失败率）来支撑迭代。

## 一句话武器
> 「多智能体 + 统一 SSE + RAG + 状态机，把『可扩展』和『可控性』做进架构里，完成从做功能到做平台的升级。」

# 项目二 · AI 临床思维训练平台（次推，体现「AI 落地 + 高并发锁」）

## 一句话版（30s）
> 「面向医学院校的 AI 临床思维训练平台，覆盖『病例库 → AI 模拟问诊 → 诊断训练 → 智能评价 → 报告导出』全闭环，用大模型角色扮演 + 可配置提示词 + SSE 流式输出 + 结构化评分，支撑 App（U3D）/ 小程序 / Web / TV 多端。我负责后端核心链路与 AI 问诊、智能评分。目前稳定服务 xx 所院校、xx 万学员、累计 xx 万次训练。」

## 2 分钟版（STAR）
- **S 背景**：临床思维训练需要一个真实、可复现的「AI 模拟患者」来问诊并给分，传统录题方式效率低、体验差。
- **T 目标**：做一套从病例下发→AI 问诊→评价→报告的完整训练闭环，且问诊要流畅（流式）、评价要可解释（结构化打分）。
- **A 行动**：
  1. 后端核心：负责全流程链路（病例下发→AI 问诊→体格/辅助检查→诊断与鉴别→进一步检查→治疗原则→评价报告），用 **protobuf + JSON 双通道**支撑多端。
  2. AI 问诊：基于通义千问做**患者角色扮演**，设计「预设问答 + id 匹配」+ 可配置提示词（角色扮演/口语化/结构化 JSON 约束），**WebFlux + SSE 流式返回**，做提示词优化与异常兜底。
  3. 智能评价：**分项打分（0.5 分粒度）+ 人文关怀评价 + 治疗原则语义匹配评分**，自动生成评价结果。
  4. 病例库与素材：基于**抽象工厂模式**重构教学素材 Excel 批量导入导出，实现病例模块化配置/审核/标签/公开管理。
  5. 并发与一致性：Redisson 公平锁做问诊并发控制，异步同步训练日志到学习空间、与中台任务中心打通。
- **R 结果**：首字响应 3s→1.2s；单批病例导入从人工 3 天→分钟级，支撑 xx+ 病例库；已服务 xx 所院校 / xx 万学员 / xx 万次训练（多学科）。
- **T**：学会了把「AI 能力」和「工程稳定性」结合——流式、评分、并发锁、多端协议。

## 5 分钟深挖版（难点/取舍/排查）
- **难点 1：问诊流式 + 稳定性。** 流式网络抖动、大模型超时、乱序 → 提示词兜底 + 有限重试 + 异常降级 + 首字延迟优化（预连接/减少前置 stage/缓存）。
- **难点 2：评价可解释、可量化。** 结构化 JSON 约束输出，0.5 分粒度分项，治疗原则用语义匹配，避免模型「瞎给分」。
- **难点 3：多端接入。** U3D 要性能用 protobuf，小程序/Web 用 JSON；服务端状态收敛，保证一致性。
- **难点 4：并发问诊。** 一次问诊有状态（预设问答 id 匹配、进度），要串行不串错 → Redisson 公平锁，粒度到「一次问诊/一个病例」。

## 高频追问 + 答案（10+）
1. **SSE 为什么用 WebFlux，不用 WebMVC？**
  → 响应式线程模型，一条长连接不占 Servlet 线程；SSE 是长连接+服务端推送，WebFlux 天然适合。注意别在 Reactor 线程做阻塞 IO。
2. **怎么做到首字从 3s 降到 1.2s？**
  → 减少到模型的前置 stage、提前建立连接/复用、流式逐 token 输出（不等整段）、必要时做 token 级缓存、优化 prompt 长度。
3. **0.5 分粒度评分怎么实现？**
  → 结构化 JSON 输出约束 + 分项定义（问诊/检查/诊断/治疗等），每项打 0.5 分；治疗原则用语义匹配（向量/相似度）而非硬匹配。
4. **为什么用 Redisson 公平锁？**
  → 问诊有先后公平性需求（学生按顺序），公平锁避免插队和饥饿；锁粒度是「一次问诊/一个病例」，不锁全局，吞吐可控。
5. **protobuf 和 JSON 为什么双通道？**
  → 性能优先端（U3D/App）用 protobuf，体积小、解析快；兼容端（小程序/Web）用 JSON 好调试；服务端做协议适配。
6. **「预设问答 + id 匹配」是什么机制？**
  → 预先定义标准问答对，用 id 关联；模型回答时匹配，保证答到点上、可给分、可复现，而非完全自由发挥导致难评分。
7. **大模型回答错了怎么办？**
  → 提示词约束 + 有限重试 + 兜底回复 + 评分扣分；对高影响场景做人工校验/审核。
8. **如何保证多端数据一致？**
  → 服务端统一状态收敛 + protobuf/JSON 统一字段，App/小程序/Web/TV 只是客户端，最终状态以服务端为准。
9. **为什么用抽象工厂重构 Excel 导入导出？**
  → 教学素材类型多（问诊/症状/检查/治疗原则）且结构不同；抽象工厂按类型创建对应处理器，新增类型只加实现，扩展性好。
10. **批量导入怎么做到分钟级？**
  → 分片读取 + 异步/线程池 + 分批入库 + 流式 POI 避免 OOM + 校验前置，失败可重试并定位到行。
11. **和中台任务中心怎么互通？**
  → 训练完成后异步同步日志/结果到任务中心，形成「训练—审核—任务—分析」数据闭环，给教学督导用。
12. **数据量/并发多大？瓶颈在哪？**
  → xx 万学员、xx 万次训练、并发问诊受大模型 QPS 限制；瓶颈在模型服务，用重试/限流/降级保护。

## 一句话武器
> 「大模型角色扮演 + 可配置提示词 + SSE 流式 + 结构化评分，落地了从病例库到评价报告的临床思维训练完整闭环。」

# 项目三 · 传染病协同训练平台（组队大厅 + 即时通信，体现「高并发 + 分布式锁」）

## 一句话版（30s）
> 「面向医疗培训多人在线协作的后端平台，提供组队大厅、公开/密码房间、成员关系管理，以及群聊/私聊实时通信。我负责领域建模、房间生命周期、WebSocket 实时链路和 Redis 高频状态。核心是**以『房间』为粒度做并发控制和状态收敛**，压测 xx 路并发、xx 条/秒、P99<200ms。」

## 2 分钟版（STAR）
- **S 背景**：传染病协同训练需要多人组队、同房间协作、即时沟通，这些都需要「房间 + 成员 + 消息」的核心模型支撑。
- **T 目标**：搭建房间管理 + 实时通信后端，保证多人并发加入/退出/解散不丢状态、消息不错乱。
- **A 行动**：
  1. **领域建模**：围绕房间、成员、消息三大对象建模，设计表结构与 REST 接口，分层架构。
  2. **房间生命周期**：公开/密码房间的创建、查询、加入、退出、房主解散，集中校验房间状态、成员身份、房主权限。
  3. **即时通信**：基于 Spring WebSocket 构建群聊/私聊链路，关联用户、房间、连接会话，按房间/目标用户路由，推送成员加入/退出事件。
  4. **Redis 高频状态**：维护在线用户、用户所在房间、房间成员关系，供连接判断/消息定位/成员列表查询，低延迟高命中。
  5. **并发一致性**：以房间为粒度引入 Redisson 分布式锁，配合权限、状态与幂等校验。
- **R 结果**：xx 路并发、消息 xx 条/s、接口 P99<200ms；高频读缓存命中 95%+，DB 压力显著下降；群聊/私聊/事件统一到一条消息通道。
- **T**：学会「把并发范围从全局收敛到单房间」的思路，以及「高频状态放缓存、可重建」的设计权衡。

## 5 分钟深挖版（难点/取舍/扩展）
- **难点 1：并发加入/解散。** 多人同时加入、重复加入、房主解散 → 房间粒度锁 + 幂等 + 状态校验，保证有序。
- **难点 2：消息路由与在线判定。** 用户在哪个房间、哪个连接 → Redis 维护会话与房间关系，避免查库。
- **难点 3：消息可靠性/乱序。** 统一消息通道 + 消息序号；离线消息、撤回作为扩展点。
- **取舍**：Redis 状态「可重建、允许最终一致」，用实时性换 DB 压力；锁粒度选「房间」是「冲突少 + 吞吐高」的平衡。
- **扩展**：多节点 WebSocket 需引入 Redis Pub/Sub 或 MQ 做跨节点路由；离线消息可落库异步补发。

## 高频追问 + 答案（10+）
1. **为什么以「房间」为锁粒度，不全局锁？**
  → 不同房间互不影响；把并发范围从全局收敛到单房间，冲突大幅减少，吞吐提升，还能按房间做隔离。
2. **在线状态为什么放 Redis？**
  → 高频读、要求低延迟；状态数据可重建，允许最终一致，避免高频查库打崩 DB。
3. **消息怎么路由到正确的人/房间？**
  → 通过连接会话关联用户与房间，按房间广播（群聊）或按目标用户精准推送（私聊）；用 Redis 查连接/房间关系。
4. **消息会不会丢/乱序？**
  → 统一通道 + 消息序号 + 服务端确认；离线消息/撤回作为后续扩展。答「当前是同节点，我清楚多节点要引 MQ 做跨节点路由」。
5. **成员加入/退出事件怎么推送给房间所有人？**
  → WebSocket 把成员变化作为事件广播到该房间；前端刷新成员列表。
6. **密码房间怎么鉴权？**
  → 加入时校验密码 + 成员身份 + 房间状态，服务端集中校验，前端只做展示。
7. **房主解散时并发处理？**
  → 解散加锁，校验房主权限，标记房间关闭并通知所有成员；处理「解散中有人加入」的竞态。
8. **压测数据怎么来的？可信吗？**
  → Jmeter 压测，xx 并发下统计消息吞吐与 P99；说明压测模型（消息频率、房间分布）及如何配置（Redis、连接池、线程数）。
9. **缓存命中 95% 怎么做到的？**
  → 在线状态/成员列表这类读多写少、且变化不频繁的数据放缓存；设置合理过期 + 一致性更新策略。
10. **为什么用 WebSocket 而不用轮询？**
  → 实时聊天需要服务端主动推送、低延迟；轮询开销大且延迟高。WebSocket 双向、长连接、性能好。
11. **WebSocket 连接怎么管理？断线怎么办？**
  → 维护连接会话与用户映射；断线重连，Redis 重建在线状态；心跳保活。
12. **如果让你做成通用 IM，怎么扩展？**
  → 加离线消息、消息持久化、已读、撤回、@、多端同步；多节点用 MQ 做跨节点路由，消息按分片/房间分治。

## 一句话武器
> 「以『房间』为并发与状态管理的核心粒度，通过 Redis 高频状态 + Redisson 分布式锁 + WebSocket 会话路由，构建了一套高并发实时协作后端链路。」

# 全项目通用追问清单（每个项目都要能随口答）

1. 你最挑战的一个点是什么？怎么解决的？
2. 如果让你重做，会改哪里？
3. 最大的线上问题/事故？怎么定位/回滚/复盘？
4. 数据指标怎么测的？可信吗？瓶颈在哪？
5. 有没有比你这方案更优的做法？为什么当时没选？
6. 团队怎么分工，你负责哪块？别人负责哪块？
7. 这个项目你觉得最有成就感/最遗憾的是什么？
8. 做完之后你怎么验证「效果真的变好了」？
9. 如果有人质疑你的技术选型，你怎么回？
10. 这个项目能复用到别的业务吗？怎么抽象？
